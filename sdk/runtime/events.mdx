`run.events()` yields `NikaRunEvent`s: a lifecycle `kind` that means the same
on both transports, the task a `task.*` event names, the engine's own status
word, and the exact engine frame on `event.raw`.

```ts events.mts
import { Nika } from '@supernovae-st/nika'

const nika = new Nika({ cwd: process.cwd() })
const run = await nika.run('hello.nika')

for await (const event of run.events()) {
  switch (event.kind) {
    case 'run.started': console.log('started'); break
    case 'task.completed': console.log('done:', event.task); break
    case 'task.failed': console.error('failed:', event.task, event.error?.code); break
    case 'run.waiting': console.log('a human gate holds the run'); break
    case 'run.settled': console.log('ended:', event.status); break
    case 'run.interrupted': console.warn('the engine lost this execution'); break
    default: break // engine.event and future kinds: event.raw.kind names the frame
  }
}
console.log((await run.result()).status)
```

```text
started
done: greeting
ended: succeeded
succeeded
```

## How many events, on which door

The vocabulary is one; the number of events is not. For the quickstart's
one-task `hello.nika`, measured on 0.123.0:

| Door | Events |
|---|---|
| Local engine | six: `run.started` → `task.scheduled` → `task.started` → `task.completed` → `engine.event` (the engine's `workflow_completed`) → `run.settled` (`succeeded`) |
| `nika serve` | two: `run.started` → `run.settled` (`succeeded`). The server streams no per-task frame, and the SDK never invents one |

A failing task adds `task.failed` locally (with `event.error`), and the
settlement reads `failed`. A human gate ends the stream with `run.waiting`
(`paused`) on both doors. Longer workflows emit more: never assert a fixed
count, and build a server-side progress view from `run.started`, the final
event and `run.status()`.

| `event.kind` | Local frame (`event.raw.kind`) | Server frame (`event.raw.kind`) |
|---|---|---|
| `run.started` | `workflow_started` | `execution.started` |
| `task.scheduled` · `task.started` · `task.completed` · `task.failed` | `task_scheduled` · `task_started` · `task_completed` · `task_failed` | none |
| `run.waiting` | `run_settled` carrying `paused` | `execution.settled` carrying `paused` |
| `run.settled` | `run_settled` carrying `succeeded`, `failed` or `cancelled` | `execution.settled` (or `execution.cancelled`, `execution.refused`) carrying the final status |
| `run.interrupted` | `workflow_interrupted` | `execution.interrupted` |
| `run.sealed` | a `run_sealed` frame, if an engine streams one | none |
| `engine.event` | every other frame (`workflow_completed`, `permit_checked`…) | every other frame |

`run.sealed` names a frame engine 0.123.0 does not stream: it writes the seal
to the run's record only. Read `result.receipt.sealed` locally, or
[`traceVerify(receipt)`](/sdk/runtime/receipts), to know whether a run is sealed.

## Rules for a reducer

- **The result is the truth.** Never infer completion from the last event you
  recognized; await `run.result()`.
- **Keep a default branch.** The set is additive: `engine.event` and future
  kinds stay visible through `event.raw` without crashing an older interface.
- **Guard `event.task`.** It is present only on events that named a task.
- **`event.status` is the engine's word**, never renamed: a waiting run reads
  `paused`.
- **`event.sequence` exists only over HTTP.** It is the server's replay
  cursor: persist it for [`attachRun()`](/sdk/remote/jobs#recover-after-a-process-restart).

## Read events late

A run keeps its most recent events, so a view opened after the result
replays them:

```ts
const run = await nika.run('hello.nika')
const result = await run.result()            // first the result,
for await (const event of run.events()) {}   // then every event the run kept
```

The bound is `eventBufferSize`, 4096 by default. Past it, the run still runs
and `run.result()` still resolves; only a late view is refused, with
`NikaEventBufferOverflowError` (`reason: 'replay_truncated'`, and
`error.observed` says how many events there were). A live view that falls more
than its `bufferSize` behind fails with `reason: 'live_backpressure'`. Neither
refusal skips an event, and neither is about the run.

## Stop a view, not the run

```ts
const observer = new AbortController()
setTimeout(() => observer.abort(), 1000)

for await (const event of run.events({ signal: observer.signal, bufferSize: 64 })) {
  console.log(event.kind)
}
```

An `AbortSignal` stops only its own view: a live loop simply ends at the
abort, without an error, while the run keeps running. It never cancels engine
work: call `run.cancel()` for that.
