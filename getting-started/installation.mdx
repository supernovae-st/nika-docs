## Install today

<Tabs>
  <Tab title="npm">
    ```bash
    npm install -g @supernovae-st/nika-client
    nika --version
    ```
    One package gives you the `nika` command and the TypeScript SDK. The
    verified release binary for your platform arrives as an optional
    dependency (macOS and Linux · arm64 and x64): the same bytes every other
    door installs. Project-local works too: `npm install @supernovae-st/nika-client`,
    then `npx nika …` and `import { Nika } from '@supernovae-st/nika-client'`.
    The [SDK README](https://github.com/supernovae-st/nika-client#readme) carries
    the full contract; the package version follows the engine's release train.
  </Tab>

  <Tab title="Homebrew">
    ```bash
    brew install supernovae-st/tap/nika
    ```
    Recent Homebrew versions gate third-party taps behind a trust prompt —
    if the install reports the tap as untrusted, run
    `brew trust supernovae-st/tap` once and retry.
  </Tab>

  <Tab title="curl">
    ```bash
    curl -LsSf https://nika.sh/install.sh | sh
    ```
    Detects platform (macOS / Linux), prefers Homebrew when `NIKA_VERSION=latest`
    and Homebrew is available, then falls back to the GitHub release binary.
    Prefer a guided page? [nika.sh/install](https://nika.sh/install) walks the
    same install step by step, alongside this raw script.
  </Tab>

  <Tab title="cargo binstall">
    ```bash
    cargo binstall --git https://github.com/supernovae-st/nika nika-cli
    ```
    Fetches the **prebuilt release tarball** (no compile — the crate ships
    [binstall metadata](https://github.com/cargo-bins/cargo-binstall) mapping
    every release asset). One honest wart until the crates.io publish: the
    binary lands as `~/.cargo/bin/nika-cli` (the crate's declared bin name) —
    add the public name once with
    `ln -sf ~/.cargo/bin/nika-cli ~/.cargo/bin/nika`.
  </Tab>

  <Tab title="nix">
    ```bash
    nix run github:supernovae-st/nika
    ```
    **Builds the exact release source** via the repo's root `flake.nix` —
    the first run compiles, the store caches it, and the binary answers as
    `nika` (the flake renames the seed crate at install, same as the
    release). `nix profile install github:supernovae-st/nika` for a durable
    install. Zero gatekeeper: no nixpkgs queue, the flake ships in-repo.
  </Tab>

  <Tab title="source">
    ```bash
    git clone https://github.com/supernovae-st/nika.git
    cd nika
    cargo test --workspace --lib
    cargo build --release -p nika-cli
    mkdir -p ~/.nika/bin
    ln -sf "$PWD/target/release/nika-cli" ~/.nika/bin/nika
    export PATH="$HOME/.nika/bin:$PATH"
    nika --version
    ```
  </Tab>
</Tabs>

## First-run verification

You already have Claude Code or Codex. You do not need a key and you do
not need to pull a model for this step.

```bash
nika --version
nika                 # the mirror, and the line to type next
nika new hello       # local starter · zero keys · no provider call
```

Run `nika` with no arguments and read the line it offers. **Your** binary
is the source of truth; on v{STATUS.version} that line is
`{STATUS.firstCommand}`, and this page is gated on saying the same thing.

It is the zero-spend first contact: a local starter created without a provider
call. `nika init` scaffolds repo-local schema
wiring and agent context when you want a repo, not before. `nika wire
<client>` is explicit MCP client setup. Installers do not mutate editor
configs automatically.

## Servers and headless Linux

Nika jails every `exec:` child and external MCP spawn inside an OS
sandbox when the host provides one: **Seatbelt** on macOS (ships with the
OS, nothing to install), **bubblewrap** on Linux. A minimal VPS image
usually does not carry bubblewrap — install it once:

```bash
# Debian / Ubuntu
apt install bubblewrap
```

Without a backend the host answers `noop`, and what that means depends on
what the workflow declares:

- **No `permits:` block** — the run proceeds (best effort). The exec
  blocklist floor still applies; nothing else changes.
- **A `permits:` block plus `exec:` tasks** — the run refuses to start
  (`NIKA-1710`). A declared boundary the host cannot enforce is a broken
  promise, so the engine fails closed instead of running unjailed.

The posture is one knob, read once at launch:

```bash
NIKA_SANDBOX=auto     # default · the behavior above
NIKA_SANDBOX=require  # refuse ANY unconfined start, permits or not
NIKA_SANDBOX=off      # proceed unconfined — attested
```

`off` is a waiver, not a silent escape: the run's journal records
`sandbox_policy` and `sandbox_waived` on its opening frame, so a sealed
trace shows you chose it. An unknown value refuses to start (`NIKA-1711`)
— a typo'd security knob never loudly defaults.

`nika doctor` shows the selection (the sandbox row names the backend or
`noop`), and `nika explain NIKA-1710` teaches the refusal with the
per-OS fix.

## Trust but verify

<Check>
  The install script lives at [nika.sh/install.sh](https://nika.sh/install.sh).
  **Read it before piping to `sh`.** It's a small POSIX shell script.

  Release binaries are published at
  [github.com/supernovae-st/nika/releases](https://github.com/supernovae-st/nika/releases)
  with SHA256 sums.

  If you download one platform archive rather than all four, verify only that
  row. Running the checksum file wholesale reports the three archives you did
  not download as failures:

  ```bash
  asset="$(find . -maxdepth 1 -name 'nika-*.tar.gz' -print -quit | sed 's#^./##')"
  test -n "$asset"
  grep -E "[[:space:]]${asset}$" SHA256SUMS | shasum -a 256 -c -
  ```
</Check>

## A real answer, later

The first run is a rehearsal. When you want a billed or local answer:

- **A local server**, when you choose to run one — not a first-run
  download. [Local models](/guides/local-models).
- **A cloud key**, when you choose to set one. Env var names live in
  [Providers catalog](/reference/providers-catalog).

Run `nika doctor`. It reports key *presence* (never values) and which
clients are wired, and it is the honest inventory of what **your** binary
can reach — not what a flag mentions.

<Note>
  **The tool you already pay for** — running a workflow on an agent seat
  you are already logged into, with no key of your own — is the
  `--access harness` class. `nika run --help` names the flag on
  v{STATUS.version}, but the class is not compiled into that release:
  `nika doctor` prints no `access` line and no `harness` rows on it. It
  ships in the next one. Until your own `nika doctor` shows those rows,
  read [Harness access](/guides/harness-access) as what is coming.
</Note>

## What gets installed

- **`nika`**, the binary (single file, no daemon, no background process)
- **Nothing else.** No service, no telemetry, no home-dir pollution beyond
  files you explicitly create with `nika init` or `nika wire`.

## Shell completions

The binary generates its own completions — no separate package, always in
sync with the verbs your version actually ships:

<Tabs>
  <Tab title="zsh">
    ```bash
    mkdir -p ~/.zsh/completions
    nika completions zsh > ~/.zsh/completions/_nika
    # once, in ~/.zshrc (before compinit):
    # fpath=(~/.zsh/completions $fpath)
    exec zsh
    ```
  </Tab>
  <Tab title="bash">
    ```bash
    mkdir -p ~/.local/share/bash-completion/completions
    nika completions bash > ~/.local/share/bash-completion/completions/nika
    exec bash
    ```
  </Tab>
  <Tab title="fish">
    ```bash
    nika completions fish > ~/.config/fish/completions/nika.fish
    ```
  </Tab>
</Tabs>

Also available: `elvish` and `powershell`. Re-run the same command after an
upgrade to pick up new verbs.

<Note>
On engines up to 0.93.x the generated script bound completions to the
internal binary name instead of `nika` — fixed on current main. If
completions don't fire after installing, upgrade and regenerate.
</Note>

