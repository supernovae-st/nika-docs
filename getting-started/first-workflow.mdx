**Goal:** write one file, run it offline, read a typed output. No API key,
no model server, nothing leaves your machine.

<Info>
  [Install Nika](/getting-started/installation) first if you have not. This
  page writes each file by hand so you learn every line; to describe a job in
  your own words instead, open the [terminal Session](/getting-started/session).
</Info>

## 1. Write the file

Create `hello.nika`:

```yaml hello.nika
nika: hello
model: mock/echo        # rehearsal model: echoes the prompt, no network
permits: {}             # explicit: this workflow touches nothing
tasks:
  greet:
    infer:
      prompt: "Say hello to a new user, briefly."
      max_tokens: 32
outputs:
  greeting: ${{ tasks.greet.output }}
```

- **`nika: <name>`** is the mark and the workflow's kebab-case identifier.
- **`model: mock/echo`** needs no key and no server — the engine echoes the
  prompt back. The mechanics are real; the "answer" is a rehearsal.
- **`permits: {}`** declares zero authority up front. A workflow that later
  touches a file, a host or a shell must say so here, or admission refuses
  it (`NIKA-SEC-004`, naming the missing permission).
- **`max_tokens`** caps the answer's length.
- **`outputs:`** names what the run hands back.

## 2. Check it, then run it

```bash
nika check hello.nika   # static audit — before a single token is spent
nika run hello.nika
```

Captured from `nika 0.123.0` on a fresh machine, offline. The audit ends
fully green (`audited · 1 task · 1 wave · permits {} · est out ≤$0.0000 · 0
hints · risk low`, then `layers · valid ✔ · access ready ✔ · capacity fit ✔ ·
run ready ✔`), and the run prints:

```text
  ✔  greet  infer · mock/echo  2ms
  1 task · 1 wave · 0 retries · 9 tok
  ── 1/1 done · unpriced (1 call) · elapsed 0.0s ─────────────────
    wrote .nika/traces
    said "mock(echo) · Say hello to a new user, brief…"
    see it whole: nika trace outputs
    rehearsal · a mock model echoed the prompt — not a real answer
    trace: .nika/traces/2026-10-24T10-44-20Z-e0ad.ndjson · 5 events · chain 6b6f6d4e…
```

`nika check` catches broken references, missing dependencies and schema
problems before any model is called, and points at the exact fix. The run
wrote a hash-chained record under `.nika/traces/`. `unpriced (1 call)` is the
honest total for a model the catalog cannot price: never `$0.00`. Verify the
latest record:

```bash
nika trace verify
```

```text
OK — 5 events · chain intact · head 6b6f6d4ebc8fe1297af1267bde6df02553547c994b2cd43deaae53cd28141098
  internally consistent (tamper-evident, not tamper-proof) — compare the head
  against the one the run printed to close the loop
UNSEALED — no run_sealed frame: the run was not signed (no signing key at run time · a run killed before its seal · or a journal cut after it) …
```

The chain is intact, but the run is `UNSEALED`: this machine has no
run-signing key yet. Mint one once, run again, and the record is signed:

```bash
nika key init
nika run hello.nika
nika trace verify     # … SEALED — the run_sealed signature verifies · key …
```

Verification re-executes nothing: it reads the record and reports the
evidence available to it. A missing key changes the verdict, not the run's
result. [Seal your runs](/getting-started/installation#seal-your-runs)
explains where the key is stored.

## 3. Ask the file three questions

<AccordionGroup>
  <Accordion title="What if a required input is missing?" icon="circle-question">
    Mark an input `required: true` (with no `default:`) and the run refuses
    to start without it (`NIKA-1708`, exit 3): admission fails, nothing
    half-executes. An input with neither `required: true` nor a `default:`
    does not stop the start: the first task that reads it fails
    (`NIKA-VAR-001`, exit 1). Callers pass values with
    `run(..., { inputs })` in the SDK or `--var key=value` on the CLI.
  </Accordion>
  <Accordion title="What if a permission is absent?" icon="circle-question">
    Admission refuses at check; the finding names the missing
    permission. An absent `permits:` block is zero authority
    (`NIKA-AUTH-006`). A declared `permits: {}` that omits a reached
    tool or path is `NIKA-SEC-004` — the plate below. The file needs
    both the named tool (`nika:read`) and the specific path
    (`./hello.nika`). `nika check --infer-permits` drafts the
    tightest block for you.
  </Accordion>
  <Accordion title="What if I switch the model?" icon="circle-question">
    One line. `ollama/llama3.2:3b` runs locally after
    `ollama pull llama3.2:3b`; a cloud provider takes its environment key
    (`export MISTRAL_API_KEY=...` for `mistral/mistral-small-latest`). A
    reasoning (thinking) model spends its thinking inside `max_tokens`, so
    raise the cap when you switch to one: `nika check` names the minimum for
    a cataloged reasoning model. The file, the check and the record keep the
    same shape; only the answer changes. `nika doctor` reports what your
    machine can reach.
  </Accordion>
</AccordionGroup>

## 4. Add a second task that depends on the first

Save this as `greet-chain.nika`:

```yaml greet-chain.nika
nika: greet-chain
model: mock/echo
permits: {}
tasks:
  greet:
    infer:
      prompt: "Say hello to a new user, briefly."
      max_tokens: 32

  critique:
    with:
      greeting: ${{ tasks.greet.output }}  # the binding IS the edge
    infer:
      prompt: |
        The greeting was: ${{ with.greeting }}
        Rewrite it shorter.
      max_tokens: 32
outputs:
  shorter: ${{ tasks.critique.output }}
```

The `with:` block is a [binding](/concepts/bindings): it names the data the
task consumes and declares the edge that orders it — greet → critique, one
declaration, no invisible edges. Tasks with no edge between them run in
parallel automatically. (For ordering without data, such as deploy after
tests while consuming nothing, use `after: { tests: success }`.) The
`outputs:` line matters too: without a consumer, `nika check` points out that
the last task's tokens would be spent unread (`[dead-spend]`).

## 5. Get structured output

Save this as `names.nika`:

```yaml names.nika
nika: names
model: mock/echo
permits: {}
tasks:
  names:
    infer:
      prompt: "Generate three names for a butterfly."
      max_tokens: 200
      schema:                          # structured output · JSON Schema
        type: object
        additionalProperties: false
        properties:
          names:
            type: array
            items:
              type: string
              minLength: 3
              maxLength: 20
            minItems: 3
            maxItems: 3
        required: [names]
outputs:
  names: ${{ tasks.names.output.names }}
```

The engine asks the provider for output that conforms (using each
provider's native structured-output mode where the [capability
rules](/reference/capabilities) allow it) and validates the reply against
your schema before passing it on. The mock validates too — it synthesizes
a conformant instance, so this exact file runs offline. Captured from
`nika 0.123.0` (`nika run names.nika --output json`):

```json
{"names":["mock","mock","mock"]}
```

`${{ tasks.names.output.names }}` indexes into the validated object, so the
output is the array itself. `additionalProperties: false` closes the shape,
so every provider returns the same keys.

On a **successful** run, `outputs:` carries the declared shape — checked
when the model answers. A failed or refused run produces no output: the
guarantee covers shape, not outcome.

## What you just built

- Workflows are YAML files: `.nika`.
- Tasks are units of work; the map key is the identity.
- Four verbs (`infer`, `exec`, `invoke`, `agent`) define what each task
  does (HTTP fetch is the `nika:fetch` builtin under `invoke`).
- `with:` (data) and `after:` (control) build the DAG — the binding IS the
  edge.
- `${{ tasks.X.output }}` crosses a task boundary in `with:`; the body
  reads `${{ with.<name> }}`.
- `schema:` checks AI output shape at answer time; `outputs:` exports the
  result.
