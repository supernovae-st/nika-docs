Start with [offline examples](/examples/offline): known inputs, exact
outputs, no provider key and no external services. The broader gallery
contains workflows with their own model, file and service requirements.
Inspect those prerequisites and permissions before running them.

The binary also includes a rehearsal gallery:

```bash
nika try 01-hello                    # the mock rehearsal · zero keys · nothing written
nika compile hello hello.nika        # write the offline lesson at an explicit destination
```

`nika try` previews an example on the mock model with zero setup: zero keys
and no model call. The mock replaces the model, not the network: an example
that fetches still reaches its host, and `nika try` names those hosts
(`may reach: …`) before the run. `nika compile`
writes only a Ready candidate to an explicit destination; showcase jobs
on these pages are copied from the YAML, not instantiated by a showcase
slug. `nika compile --list` names exact skeletons. Unknown intent stays
incomplete and does not pick a substitute.

<p className="mt-2 text-sm text-center opacity-80">**Start from a workflow.** Run `nika try` with no argument to see the gallery built into the binary: a numbered learning path and a shelf of ready-made jobs, each marked with the verbs it uses. `nika try <name>` previews one on the mock model. *The listing is captured from the real CLI on nika 0.121.0.*</p>

The YAML you read here is projected verbatim from
[`nika-spec/examples/`](https://github.com/supernovae-st/nika-spec/tree/main/examples),
where each file passes the same conformance gate as the spec's own test
suite. That validates the file against that contract; it does not prove
that an external integration is configured or that a model will produce
a useful result. A mock rehearsal proves neither a live integration nor
an AI answer.

Together with the numbered learning path that `nika try` lists, these
workflows exercise **all {CANON.builtins} builtins** and the
{CANON.verbs} verbs. Each job page ends with a **Run it** section: the
mock rehearsal, the sample files to download, and what the real run needs.

## How to read a workflow diagram

Tasks are colored by verb, the same palette everywhere in the Nika
universe:

```mermaid
flowchart LR
  A["infer · call a model"]:::infer --> B["exec · run a process"]:::exec
  B --> C["invoke · call a tool"]:::invoke --> D["agent · drive a loop"]:::agent
  classDef infer fill:#5b8cff22,stroke:#5b8cff,color:#5b8cff
  classDef exec fill:#ff7a3c22,stroke:#ff7a3c,color:#ff7a3c
  classDef invoke fill:#22d3ee22,stroke:#22d3ee,color:#22d3ee
  classDef agent fill:#b07bff22,stroke:#b07bff,color:#b07bff
```

## The rules every example obeys

- **One verb per task** · `infer`, `exec`, `invoke` or `agent`.
- **The binding IS the edge** · `${{ tasks.X.* }}` lives in `with:`
  (data) — each reference declares a typed edge — and `after:` orders on
  state. The DAG has no invisible edges, and the body reads
  `${{ with.<name> }}`, never `tasks.*` (`NIKA-VAR-021`).
- **Local by default** · a showcase that calls a model names a local
  Ollama model (`ollama/qwen3.5:4b` for most): zero API keys, inference
  stays on your machine. Cloud providers appear only as swap hints, never
  as the default.
- **Projection, not copy-paste** · these pages and the
  [nika.sh use cases](https://nika.sh/use-cases) render the same spec
  files, projected by the spec's `showcase-projector.py`; nobody edits
  the copies by hand.

Repeat an AI task every week? Describe it in the
[terminal Session](/getting-started/session) and keep the `.nika` file it
writes.
