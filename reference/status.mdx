## What can I install?

| Product | Version these docs target | Next step |
| --- | --- | --- |
| Native engine and CLI | **v{STATUS.version}** · build {STATUS.engineSha} | [Installation](/getting-started/installation) |
| TypeScript SDK | **{SDK.package}@{SDK.sourceVersion}** | [SDK quickstart](/sdk/start/quickstart) |

The SDK bundles a native engine and requires Node.js 22 or newer. Its package
version is a separate publication from the CLI. A merged SDK change or a newer
engine release does not update an installed npm package.

<Tip>
  Start with the SDK if you are adding workflows to an app. Start with the CLI
  if you want to check and run a `.nika` file from your terminal.
</Tip>

## What does the engine snapshot prove?

The engine fields below are projected from one selected published stable release.
The installer verifies its checksums and attestation; the projector checks the
binary's reported version and build against that release's tag before writing.

| Field | Value | Source |
| --- | --- | --- |
| Engine version | v{STATUS.version} | Published GitHub release and `nika --version` |
| Build identity | {STATUS.engineSha} | The binary's version banner, checked against the release tag |
| Publication date (UTC) | {STATUS.lastUpdated} | The selected release's publication timestamp |
| Catalog providers | {STATUS.providers} | `nika catalog --json` on that binary |
| First command | {STATUS.firstCommand} | A command validated against that binary |

The publication date is not the date of the last website build. For the full
inventory, including release records with no attached assets, see
[Releases](/changelog/releases).

## Language facts have a different owner

The specification supplies **{CANON.verbs} verbs**, **{CANON.builtins} builtins**
and **{CANON.templates} skeletons** through the shared canon projection.
Its **{CANON.providers} named providers** describe the language contract; the
engine's catalog can contain additional adapters. See
[Providers](/reference/providers-catalog) and
[Sources and synchronization](/reference/knowledge-system).

Crate totals, test totals, architectural decisions and work on engine `main`
are development records. They do not prove that a feature is in the binary you
download. The [roadmap](/changelog/roadmap) keeps future work separate from releases.

## How updates reach these pages

The hourly [release sync](https://github.com/supernovae-st/nika-docs/actions/workflows/release-heal.yml)
collects published stable releases, verifies the selected native release, and
projects both the release index and the engine snapshot. It proposes the
generated files, dispatches the documentation checks, and merges only after
those checks and normal branch protection permit it. Mintlify then deploys `main`.

The native snapshot updates `version`, `engineSha`, `providers`, `firstCommand`
and `lastUpdated` together. It does not rewrite historical development counts,
publish an npm package, or turn a roadmap proposal into a released feature.
Failed validation leaves the previous documentation in place and a failed sync
run to investigate.

For contributors, run these commands from the documentation repository with the
verified release selected through `NIKA_BIN`:

```bash
python3 scripts/release_catalog.py --refresh
bash scripts/mintlify-snapshot.sh
python3 scripts/release_catalog.py --refresh --check
```
