Point `model:` at a local server and model inference stays on your
machine. Other steps in the workflow can still contact services, such as
a URL fetch, an MCP server or a hosted model chosen for another task.
This page is the ladder, from the server built into `nika` to production
servers.

## 1. Built in: `nika model pull` and `nika model serve`

The `nika` binary carries its own local inference: no daemon to install,
one models folder (`~/.nika/models`).

<Steps>
  <Step title="Pull a GGUF from the Hugging Face Hub">
    ```bash
    nika model pull unsloth/Qwen3-4B-Instruct-2507-GGUF:Q4_K_M
    ```

    The size prints before the download, and a file of 2 GiB or more asks
    you to confirm (`--yes` for scripts). An interrupted pull resumes, and
    `HF_TOKEN` authenticates gated repositories. The pull is a command you
    run, not a workflow step, so no `permits:` block governs it.
  </Step>
  <Step title="Serve it">
    ```bash
    nika model serve --model unsloth/Qwen3-4B-Instruct-2507-GGUF:Q4_K_M --model-id qwen3-4b
    ```

    A foreground, OpenAI-compatible server starts on `127.0.0.1:8712`:
    loopback only, one generation at a time, `Ctrl-C` stops it. Its banner
    prints the two lines a workflow needs.
  </Step>
  <Step title="Point a workflow at it">
    In another terminal:

    ```bash
    export NIKA_LLAMACPP_BASE_URL=http://127.0.0.1:8712
    ```

    ```yaml
    model: llamacpp/qwen3-4b
    ```

    The served model rides the `llamacpp` provider, so the file needs no
    new syntax.
  </Step>
</Steps>

`nika model list` shows what is on disk and `nika model rm <owner/repo>`
reclaims it.

<Warning>
  In 0.124.1 the built-in server loads **Qwen3-family GGUFs only**. A GGUF
  of another family is refused when it loads; serve it with one of the
  servers further down this page.
</Warning>

### Gear One: the pick `nika welcome` proposes

`nika welcome` and `nika doctor` propose one local pull sized to your
memory, under the name **Nika Gear One**. The pick is a table shipped in
the binary:

| Memory | Tier | `nika model pull …` | Download |
|---|---|---|---|
| 64 GB and more | workstation | `unsloth/Qwen3.8-27B-GGUF:UD-Q5_K_M` | 40 GB |
| 24 GB and more | default | `unsloth/Qwen3.8-27B-GGUF:UD-Q4_K_M` | 16.5 GB |
| 16 GB and more | standard | `unsloth/gemma-3-12b-it-GGUF:Q4_K_M` | 7.4 GB |
| 8 GB and more | lite | `unsloth/Qwen3-4B-Instruct-2507-GGUF:Q4_K_M` | 5.5 GB |

None of these picks is marked verified in 0.124.1. The standard pick is a
Gemma 3 model, which `nika model serve` cannot load: on a 16 to 23 GB
machine, either pull the lite pick for the built-in server, or serve the
Gemma file with llama.cpp's `llama-server` or LM Studio (below).

## 2. The one-command path: Ollama

Install [Ollama](https://ollama.com), then:

```bash
ollama pull qwen3.5:4b
```

That's it. In any workflow (the same tag the Homebrew install suggests;
the `nika init` scaffold starts smaller, with `ollama/qwen2.5:0.5b`):

```yaml
model: ollama/qwen3.5:4b
```

`nika doctor --ping` confirms the wiring: it connects to the local ports
you configured and reads their model lists, without running a model.

<Tip>
  `qwen3.5:4b` is small enough for most laptops and good enough for
  structured extraction. It thinks before it answers, and the thinking
  counts against `max_tokens`: size the ceiling for both, and if a run fails
  `NIKA-INFER-004`, the thinking ate the budget. Swap the tag for anything in
  the [Ollama library](https://ollama.com/library): `llama3.2`, `mistral`,
  `phi4`, larger Qwen variants. Rehearse with `model: mock/echo` when you want
  zero daemon and zero keys: mock simulates the model reply; it does not
  disable tools or effects.
</Tip>

## 3. Any Hugging Face GGUF through Ollama

Ollama pulls directly from the Hugging Face Hub. Any public GGUF repo
works, no account needed:

```bash
ollama run hf.co/bartowski/Llama-3.2-3B-Instruct-GGUF
```

Pick a quantization explicitly with a tag:

```bash
ollama run hf.co/bartowski/Llama-3.2-3B-Instruct-GGUF:Q4_K_M
```

Then reference it in the workflow exactly as pulled:

```yaml
model: ollama/hf.co/bartowski/Llama-3.2-3B-Instruct-GGUF:Q4_K_M
```

Rule of thumb for quantizations: `Q4_K_M` is the sane default (quality per
GB), `Q8_0` when you have RAM to spare, `Q2/Q3` only when memory is tight.
The [Hub's GGUF filter](https://huggingface.co/models?library=gguf) lists
every compatible repo.

## 4. LM Studio: the visual browser

Prefer a GUI? [LM Studio](https://lmstudio.ai) browses Hugging Face,
downloads models with a click, and serves an OpenAI-compatible endpoint.
Start its server, then:

```yaml
model: lmstudio/<the-model-id-shown-in-lm-studio>
```

## 5. Servers: llama.cpp and vLLM

For shared machines and production:

- [llama.cpp](https://github.com/ggml-org/llama.cpp) `llama-server` serves
  a GGUF: `model: llamacpp/<model>`
- [vLLM](https://docs.vllm.ai) serves full-precision Hub models at
  datacenter throughput: `model: vllm/<hub-repo-id>`

Both speak the same OpenAI-compatible dialect; the prefix picks the
provider, nothing else in the file changes. `NIKA_<ID>_BASE_URL` (for
example `NIKA_VLLM_BASE_URL`) points a provider at another host or port.

## Checking what's wired

```bash
nika doctor          # offline: keys by presence, the local providers, pulled models
nika doctor --ping   # also connects to configured local ports and reads their model lists
```

Doctor prints a fix for each missing piece and never applies it. Then audit
the file before a run:

```bash
nika check my-workflow.nika
```

A local model has no catalog price, so the cost line marks it **unpriced**,
never `$0`:

```text
 ⚠  COST     bounded portion $0.0000 no total ceiling · 1 unpriced task · prompts, exec + mcp unpriced · prices 2026-10-12
   summarize  ollama/qwen3.5:4b  UNBOUNDED — no catalog price (local model; spend not metered)
```

`--max-cost-usd` never blocks local or mock work: it bounds what the catalog
can meter. [Cost honesty](/guides/cost-honesty) explains why.

## Thinking time is budgeted for

A local thinking model can need minutes for one completion on consumer
hardware. When a task declares no `timeout:`, a buffered provider call gets
**600 s**, local or cloud alike: the transport cannot tell a model that is
thinking from a dead connection. A streaming call has no total deadline;
the idle-read guard ends a stream that stays silent for 600 s.

When a task needs a different bound, its own `timeout:` governs the
provider deadline directly:

```yaml
deep_review:
  timeout: "7m"                # Go-duration · bounds the task AND the provider call
  infer:
    prompt: "Review this diff…"
```

Full semantics: [YAML reference · Timeouts](/reference/yaml-syntax#timeouts).

## Swapping between local and cloud

The file does not change shape. One line moves the workflow between a
laptop and an API:

```yaml
model: ollama/qwen3.5:4b         # local · unpriced · private
# model: openai/gpt-4.1-mini     # cloud · pin a cataloged id
# model: xai/grok-4.3            # cloud reasoning model · give it max_tokens of 256 or more
# model: huggingface/…           # Hub-served
# model: nvidia/…                # NIM
```

<Note>
  The permits boundary applies either way: a `permits:` block with no
  `net.http` entry means the workflow cannot reach the network even if the
  model could. Local model + closed permits = fully air-gapped AI work.
</Note>
